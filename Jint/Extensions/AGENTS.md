# Agent instructions: where Jint does not trust the BCL

> **Read this when:** You parse number text, classify white space, sort with a comparer that script supplies, or hand script text to a BCL parser, anywhere in `Jint/`. This file governs the whole assembly, not just this directory.
>
> This is one of the co-located instruction files indexed from the repository-root
> [`AGENTS.md`](../../AGENTS.md). Read that first — it carries the build and test commands, the branch to
> target, and the conventions that apply to every file in the repository. Nothing below is
> repeated there.

`Jint` targets `net10.0` only, so write a call site against the .NET 10 BCL directly; there is no polyfill container and no `#if` for a target framework. What follows are the places where the BCL's answer is not ECMAScript's, whatever the runtime.

**Sorting with a script comparer.** `SortExtensions.StableOrder` is a hand-written merge sort rather than a call to `OrderBy` because a JavaScript comparison function is allowed to be inconsistent, and a sort has to finish anyway: LINQ's sort on .NET Framework was a quicksort with no depth limit and no fallback, which spun forever on such a comparer. Sorting and searching are where library implementations differ most; do not assume another one terminates.

**Number parsing replaces the BCL everywhere.** .NET Framework's `double.Parse`, which Jint once ran on, is not IEEE correctly-rounded: it lands one ULP off for about one in sixty-five 18-digit operands, fails rather than saturating to an infinity on overflow, loses the sign of `-0`, and rejects a leading `+` under the styles the spec lanes passed it. ECMA-262 makes every string-to-number conversion one rounding to the nearest Number, so the answer may not depend on the platform's parser — and `parseFloat`, `Number(…)` and `JSON.parse` disagreed with each other on `net472` for the same digits (sebastienros/jint#3532). `NumberParser.TryParseDouble` reads the digits itself and is the only route any of them, `TemporalHelpers`, or the numeric-literal reader takes to a `double` — a literal carrying a fraction, an exponent or more digits than a `ulong` holds reached the *parser's* `double.Parse` and moved for the same reason (sebastienros/jint#3533), so `AstExtensions.NearestDouble` re-reads it here too. It is **exact rather than approximately right** — a `ulong` fast path and a Clinger scaling by an exactly-representable power of ten settle the common shapes in one rounding, and everything else goes through `BigInteger` division against the rounding boundary. A "close enough" decimal parser is the failure mode here; `Jint.Tests/Runtime/StringToNumberPrecisionTests.cs` holds it to an exact oracle.

**And being exact obliges it to be bounded first.** The size of an exact value is the caller's choice, so `parseInt('9'.repeat(1e8))` may not become an allocation — and `parseInt` arrived at the same routine from the other side, having accumulated its digits into a `double` and rounded once per digit, in every radix (sebastienros/jint#3534). An n-digit integer in radix R is at least R^(n-1), so the magnitude follows from the digit count alone: at 311 digits in radix 10 — 1026 in radix 2, 201 in radix 36 — the answer is an infinity whatever the remaining text says and the scan stops there, which caps the widest exact value ever built at about 130 bytes. `TryParseRadixInteger` settles everything under 2^64 in a `ulong`, a radix that is a power of two in a shift with a sticky bit, and every other radix by building the exact integer inside that bound. Anything added here inherits both halves: settle the magnitude from the length, then be exact inside the bound it leaves.

**White space is a classification rather than a parse.** `char.IsWhiteSpace` answers a Unicode question, not an ECMAScript one, and over the whole Basic Multilingual Plane it differs from JavaScript's set on exactly two code points — in both directions: it counts U+0085 NEXT LINE, which is category `Cc` and in neither the `WhiteSpace` nor the `LineTerminator` production, and it does not count U+FEFF ZWNBSP, which is `WhiteSpace`. So `trim`, `parseInt`, `parseFloat`, `Number(…)` and `BigInt(…)` skipped a NEL the parser treats as an ordinary character, and read a lone U+FEFF as `NaN` (sebastienros/jint#3539). `Character.IsJsWhiteSpace` is the one definition every language-level lane reads — the trim halves, the string-to-number lanes, the `\s` character class and `RegExp.escape` — with `IsJsLineTerminator` and `IsJsWhiteSpaceExceptLineTerminator` for the two callers that need the productions apart. Its `Space_Separator` members are **enumerated rather than read from `char.GetUnicodeCategory`**, because a runtime's Unicode table moves between versions and one definition that moves under an embedder is not one; `Jint.Tests/Runtime/WhiteSpaceDefinitionTests.cs` checks the enumeration against the running runtime's table, and sweeps every lane over all 65,536 code units against a set it builds itself. Two sets legitimately are not this one and must not be folded into it: `JsonParser.IsWhiteSpace` is JSON's, which `JSON.parse` defers to ECMA-404 and which is TAB, LF, CR and SP only, and `DefaultTimeSystem` trims host date text with `string.Trim()` because everything the Date Time String Format does not match is implementation-defined anyway.

**A BCL parser reading raw script text has tolerances that are not the styles it was handed.** `long.TryParse`, `int.TryParse` and `uint.TryParse` end a number at a U+0000 and accept however many follow it, the way a C string terminates. That one is the parser's own and no `NumberStyles` flag turns it off — dropping `AllowTrailingWhite` changes nothing — while U+0000 is category `Cc` and in neither white-space production, so it padded a `StringNumericLiteral` on `Number`'s whole-number fast path and an index on `ArrayInstance.ParseArrayIndex`, where `uint.TryParse` took the framework's white space and a leading sign as well (sebastienros/jint#3541). Both now check the last character against what the grammar allows there rather than trusting a style set to say it: an array index ends in a decimal digit, and so does every whole number the fast path exists for — the one legal spelling that does not, `"12."`, falls through and reads the same from the general lane. A lane that hands script text to a BCL parser owes the same guard.
